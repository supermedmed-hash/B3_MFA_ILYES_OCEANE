Explication Pédagogique : Active Directory et Identité Hybride

Note pour le Jury de Soutenance

1. Notre Contexte de Projet

Dans notre infrastructure Smart Office 2.0, l'annuaire d'entreprise (Active Directory) est hébergé localement sur un serveur Windows 2019 dans la zone GNS3 gérée par Océane.

Dans la configuration actuelle de notre MVP (Proof of Concept), l'application Node.js s'appuie sur une table users dans la base PostgreSQL locale (pour démontrer le fonctionnement du backend métier) plutôt que d'être jointe informatiquement à l'AD pour chaque requête.

2. Évolution vers la Synchronisation Azure AD (Entra ID)

Cependant, notre architecture hybride (VPN IPsec) nous offre une voie d'évolution "Enterprise-Grade" pour l'identité. Voici comment l'AD On-Premise interagit avec le Cloud dans un scénario de production :

1 Mise en place de l'Agent de synchronisation : Au lieu d'ouvrir les ports LDAP (389) au travers du VPN de pfSense (ce qui est une mauvaise pratique de sécurité pour une WebApp exposée sur internet), on installe l'outil Azure AD Connect sur le serveur Windows 2019 local.

2 Réplication unilatérale : Cet outil synchronise les comptes AD locaux vers le tenant Microsoft Azure (Entra ID). Le flux est sortant du réseau local vers le Cloud.

3. Haute Disponibilité de l'Authentification

Comme précisé dans notre strategie_deploiement_azure.md : "Grâce à la réplication AD entre Océane et Azure, si le site local tombe, l'authentification cloud reste possible."

C'est tout le but de cette architecture. L'application Web hébergée dans l'Azure App Service pourrait interroger le tenant Azure Entra ID directement via des Tokens (OAuth). Même si le routeur pfSense coupe le VPN (perdant l'accès aux bases SQL métiers locales), la fonction d'authentification des employés survivrait, prouvant l'intérêt du Cloud Hybride en matière de continuité de service de l'identité.
